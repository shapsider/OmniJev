# 让决策模型"看见"：OmniJev 试图把图像接进 Jev 的决策闭环

> 一句话版本：Jev 能把非结构化状态变成结构化决策，但它读的是文字。OmniJev 在同一套有限选择接口上，把相机图像、腕部视角也塞进了状态里——不训练、不改权重，只改接口。

---

## 一、起点：Jev 很强，但它读的是文字

Jev 做的事很干净：**把一团非结构化的状态，映射成对预设候选的结构化选择**。路由、分类、有限动作选择——它给的不是一段自由文本，而是一个可判定、可记录、可回放的决策。

这个设计有个很实在的好处：决策是**有边界**的。候选集是你定的，输出落在候选内才算有效，落在候选外可以显式判为"无效"，证据不足可以显式"弃权"。在需要追责和复盘的场景里，这比让模型自由发挥靠谱得多。

但它有个前提：状态得是文字能说清的。

## 二、缺口：具身决策的信号，本来就是视觉的

机器人做决策时，真正决定成败的那些信息——目标物体现在在哪、夹具有没有对准、托盘被挪走了没有、挡板是不是挡在路径上——几乎全是**图像**。

你可以用文字去描述它们，但那意味着你得先有一个"看图说话"的前置模块，而且它说什么、漏什么，你无从校验。更直接的做法是：**让决策模型自己看图。**

这就是 OmniJev 的出发点。

## 三、OmniJev 做了什么：改接口，不改模型

先说清楚一件事：**OmniJev 没有训练任何东西**。没有微调，没有分类头，没有动权重。它是一层接口。

```
调用方定义：问题 + 候选集 + 状态
        ↓
状态里可以带：文本块 / 图像块（image_url base64）/ 音频块（input_audio）
        ↓
一个冻结的视觉语言模型（当前是本地 Nemotron 3 Nano Omni Q4_K_M）
        ↓
两种输出模式：
  · letter 模式：max_tokens=4 + 取首 token top-10 logprobs
                 → 候选字母上的 softmax，得到概率分布
  · json 模式：json_schema enum 硬约束输出
        ↓
四态显式区分：决策 / 弃权 / 无效 / 超时
        ↓
留痕：messages_sha256 + 延迟 + token 用量，请求级全量归档
```

三个值得单独拎出来的设计：

**1. 有限选择是刻意的。** 不是"让模型回答"，而是"让模型在 A/B/C/D 里选"。这让"不确定"有了表达方式——四个弃权探测族里，模型返回的都是 `insufficient evidence`，而不是硬猜一个。

**2. 概率是免费的副产品，但别当置信度用。** 概率条来自首 token 的候选字母 logprobs，代码里明确标了 `calibrated: false`。它是相对倾向，不是校准后的正确率。这一点在下面讲基准时很重要。

**3. 每次请求都留痕。** 输入哈希、延迟、token 用量逐条记录；具身场景里模型收到的每张图像单独归档 SHA-256。这意味着任何一次决策都能被翻出来重看。

## 四、看得见的证据

### 4.1 十二族决策探测：它到底在看什么

我们从 `results/scored-records.jsonl` 里每个探测族取了一条真实记录，把模型**实际收到的 PNG**、问题、选项、候选概率分布画在一张图上：

> **配图 2**：`docs/media/omnijev-decision-probes.png`（十二族决策画廊）

十二族覆盖了干净读图、计数、空间关系、图文冲突、双帧序列，以及四类"证据不足"的情形：没有图、属性不可观测、空白帧、答案在候选集之外。

结果：**208 个非音频请求全部有效且正确**；四类弃权场景全部返回 `insufficient evidence` 而不是猜测。

有一格是红的：**音频**。客户端完整实现了 `input_audio` 块，但当前后端直接拒了——HTTP 500，`audio input is not supported ... you may need to provide the mmproj`。所以今天 OmniJev 的实际模态是**文本 + 图像**，音频是"接口就绪、后端未开"。这一点我们不想含糊。

## 五、公开基准：我们测出了什么，没测出什么

这一段是我们最想让你先看的部分。

我们在四个公开多模态子集上跑了对比：MMStar（300 题）、MMBench DEV EN（60 题）、MMAD 工业缺陷 VQA（45 题）、StreamingBench 八帧视频因果（20 题），共 425 题、1700 次正式请求，同一台机器、同一个冻结模型，四种策略横向比。

> **配图 7**：`docs/media/omnijev-benchmarks.png`（四子集 × 四策略）

**测出来的：**

- **快**：相对预算式推理基线，四组延迟中位数分别快 **13.6×、10.0×、8.7×、6.8×**
- **省**：OmniJev 平均只生成 3 个 token，含多模态输入在内总 token 省 **85.79% / 66.16% / 71.80% / 51.26%**

**没测出来的：**

- **准确率没有独立增益。** 四个子集上，OmniJev 与"直接让同一个模型简短作答"的准确率**完全持平**（66.67% / 90.00% / 86.67% / 85.00%）
- 在 MMStar 上，预算式推理反而**高 5.67 个百分点**（72.33% vs 66.67%）。数学子集是最直白的反例：短答对 27/50，推理对 45/50
- 八帧视频的中位延迟仍是 **2.98 秒**——这不能用来宣称亚秒级控制或高频实时决策

所以我们自己在结论文档里写的是：**今天的 OmniJev 不足以支撑"独立新范式"的说法**，建议定位为 *training-free、time-limited 的多模态选择性推理与决策系统*。

这个定位有点克制，但它是站得住的那个。真正值得往下做的增量不在"比短答更准"，而在**调度与状态管理**：什么时候升级到长链推理、什么时候弃权、连续输入下什么时候才重新处理媒体。

## 六、今天能做什么，还不能做什么

**能做的：**

- 把带图像的状态压到有限候选上，拿到一个可判定、可留痕的决策
- 概率分布（未校准）与显式弃权
- MuJoCo 仿真执行、安全预演、双相机采集、接触反馈、轨迹回放
- 请求级证据归档，逐条可复盘

**还不能做的：**

- 音频模态（后端未支持）
- 端到端视觉规划。双相机、原始 RGB、不给物体与目标真值坐标的条件下，OmniJev 和直接基线都在 60 步预算内耗尽，**0/1**。相机链路是通的、图像确实到了模型，跟不上的是决策质量
- 宣称准确率优于直接短答

上面三个具身动图属于**技能模式**：模型在特权仿真状态下选预设技能，程序执行 IK 轨迹。它不是端到端视觉规划，请不要当成后者读。

## 七、十分钟跑起来

```bash
# 1. 装 SDK
pip install -e .
# 2. 下载模型（Nemotron 3 Nano Omni Q4_K_M）
# 3. 起推理后端 + HTTP 服务
# 4. 起具身工作台
bash run_embodied.sh
```

如果要导出轨迹动图，不需要跑模型后端——从已归档的 episode 直接重建：

```bash
python scripts/export_trajectory_frames.py \
  --episode results/embodied/skills-seed0/transfer-0-omnijev.json \
  --out embodied/tools/trajectory-media/data/transfer-omnijev
```

细节见仓库 README 的 Quick Start 和 `embodied/tools/trajectory-media/README.md`。
